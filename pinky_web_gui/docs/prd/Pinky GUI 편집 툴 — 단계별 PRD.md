# Pinky GUI 편집 툴 — 단계별 PRD

2026-10-11 · 초안 (결정이 필요한 항목은 6절)

## 0. 공통 개요

### 0-1. 배경과 문제

관제 GUI(`frontend/`)는 프레임워크 없이 손으로 쓴 정적 HTML/JS다. 화면 구성(패널, 탭, 버튼 문구, 색)이 `index.html`, `app.js`(1555줄), `style.css`에 흩어져 있어서 화면을 바꾸려면 코드를 직접 고쳐야 한다. 지금 사용자가 화면에서 바꿀 수 있는 것은 "레이아웃 편집" 버튼으로 하는 **패널 3개(지도, 사이드바, 명령 이력)의 위치와 크기**뿐이고, 그것도 브라우저 `localStorage`(`pinky.layout.v2`)에만 저장된다. 다른 PC나 브라우저에서는 보이지 않는다.

### 0-2. 목표

코드를 쓰지 않고 별도의 편집 화면에서 관제 GUI의 구성을 바꾸고, 그 결과를 **서버에 저장해 모든 관제 화면에 적용**한다.

| 편집 대상 | 예 |
| --- | --- |
| 패널 배치 | 지도, 사이드바, 이력 패널 위치와 크기, 패널 추가/숨김 |
| 사이드바 탭 | 탭 순서, 이름, 표시 여부 (로봇 / 시스템 / 경로 / 조작 / 좌표) |
| 위젯 | 탭 안에 들어가는 위젯의 순서와 표시 여부 (예: LiDAR 오버레이, 수동 조작 패드) |
| 문구 | 버튼 라벨, 패널 제목, 안내 문구 |
| 테마 | 색 토큰(`--accent`, `--bad` 등), 글자 크기, 라이트/다크 각각 |

### 0-3. 목표가 아닌 것 (비목표)

- 새 기능이나 새 명령을 만드는 노코드 도구가 아니다. 위젯은 코드가 제공하는 것만 고른다.
- 로봇 명령의 종류, 허용 포인트, 권한(manager/operator), 인증을 편집 대상으로 삼지 않는다.
- 로봇 추가와 `robots.yaml` 편집은 하지 않는다. 기존 "로봇 추가" 안내 팝업이 맡는다.
- 모바일 전용 레이아웃, 여러 사용자의 동시 실시간 편집은 하지 않는다.

### 0-4. 현재 코드에서 재사용할 것

- 격자 레이아웃: `app.js`의 `GRID`(24x20), `DEFAULT_RECTS`, `dragRect()`(이동/크기 순수 계산), `validRect()`. 이 계산은 편집 툴에서도 그대로 쓴다.
- 색 토큰: `style.css`의 `:root` 변수(라이트)와 `[data-theme="dark"]`.
- 탭: 섹션의 `data-tab`, `data-tab-label` 속성 (`setupTabs()`).
- 서버: `backend/main.py`의 `/api/...` REST, 쿠키 세션과 `Auth.allows(role, MANAGER)` 권한 확인, `StaticFiles` 서빙. `/console`처럼 별도 화면 경로를 이미 하나 갖고 있다.
- 설정 저장 방식: `config/*.yaml`을 서버가 읽는 패턴 (`robots.yaml`, `points.yaml`, `zone.yaml`).

### 0-5. 아키텍처 결정

핵심은 **화면을 "코드"가 아니라 "명세(spec) 파일"로 만들고, 편집 툴은 이 파일만 고친다**는 것이다.

```
 편집 툴 (/editor)  --저장-->  config/gui_layout.yaml  --읽기-->  관제 GUI (/)
   (manager 로그인)             (서버가 검증 후 저장)            (명세대로 화면을 구성)
```

- **명세 파일**: `config/gui_layout.yaml` (JSON 스키마로 검증). 패널 사각형, 탭 목록, 위젯 목록, 문구 덮어쓰기, 테마 토큰을 담는다. 파일이 없거나 깨졌으면 지금의 기본 화면(`DEFAULT_RECTS` 등)으로 돌아간다.
- **편집 툴**: 같은 서버가 서빙하는 별도 페이지 `/editor` (`frontend/editor/`). 프레임워크와 빌드 도구 없이 정적 HTML + JS로 만든다 (기존 GUI와 같은 원칙, npm 불필요).
- **미리보기**: 편집 툴 안에서 관제 GUI를 `iframe`으로 띄우되 mock 데이터로 돌린다. 실제 로봇 명령은 편집 중에 나가지 않는다.
- **관제 GUI 쪽 변경**: 하드코딩된 구성을 명세를 읽어 그리는 렌더러로 바꾼다. 이것이 이 작업의 가장 큰 비용이다 (Step 1).

### 0-6. 공통 원칙

1. **안전 요소는 편집 대상이 아니다.** 비상 정지 바(`#estopBar`), 연결/구역 칩, 알람 바, 확인 팝업은 항상 보이고 삭제, 숨김, 문구 변경이 불가능하다. 편집 툴의 UI에서 아예 선택되지 않게 하고, 서버 검증에서도 거부한다.
2. 편집은 **manager 로그인**이 필요하다. 저장 API는 `Auth.allows(role, MANAGER)`로 막는다.
3. 서버는 저장 전에 스키마와 불변 조건(원칙 1, 패널 겹침/범위, 알 수 없는 위젯 ID)을 검증한다. 클라이언트 검증만 믿지 않는다.
4. 저장 전에 직전 버전을 `config/gui_layout.yaml.bak`(또는 이력)으로 남기고, 편집 툴과 관제 화면 양쪽에서 "기본값으로 되돌리기"가 된다.
5. 잘못된 명세가 들어와도 관제 화면은 **항상 뜬다**. 렌더러는 검증 실패 시 기본 화면으로 폴백하고 알람 바에 한 줄 알린다.
6. 각 Step은 로봇 없이 mock 모드로 테스트한다. 실제 로봇 연결 확인은 사용자가 한다. `tests/`에 명세 검증과 API 테스트를 추가한다.
7. 기존 ROS 코드와 `docs/interfaces.md`의 토픽/명령 규약은 건드리지 않는다. 새 코드는 `pinky_web_gui/` 안에만 둔다.

### 0-7. 로드맵

1. **Step 0** 명세 스키마 확정과 위젯 목록 정리 (코드 변경 없음)
2. **Step 1** 관제 GUI를 명세 기반 렌더러로 전환 (겉모습은 그대로)
3. **Step 2** 저장 API와 `/editor` 뼈대 (명세 보기, 저장, 되돌리기)
4. **Step 3** 패널 배치 편집 (끌기, 크기 조절, 탭 구성)
5. **Step 4** 문구와 테마 편집, 라이트/다크 미리보기
6. **Step 5** 위젯 추가/숨김, 프리셋, 버전 이력 (선택)

## Step 0. 명세 스키마와 위젯 목록

코드를 쓰기 전에 "무엇을 편집할 수 있는가"의 경계를 문서로 정한다.

**할 일**
- 현재 화면을 위젯 단위로 분해해 표로 만든다. 예: `robot-cards`, `proc-list`, `route-planner`, `scan-toggles`, `drive-pad`, `click-points`, `history-table`, `map-canvas`. 각 위젯에 ID, 기본 위치, 의존하는 DOM ID와 JS 함수, "삭제 가능 여부"를 적는다.
- `gui_layout.yaml` 스키마 초안을 `docs/gui_layout_schema.md`에 쓴다.
- 편집 가능/불가 목록을 확정한다 (0-6의 원칙 1 포함).

**스키마 초안**

```yaml
version: 1
grid: {cols: 24, rows: 20}
panels:
  map:  {x: 0,  y: 0,  w: 18, h: 16}
  side: {x: 18, y: 0,  w: 6,  h: 16}
  hist: {x: 0,  y: 16, w: 24, h: 4}
side_tabs:                 # 순서가 곧 표시 순서
  - {id: robots, label: 로봇,   visible: true}
  - {id: system, label: 시스템, visible: true}
  - {id: route,  label: 경로,   visible: true}
  - {id: control, label: 조작,  visible: true}
  - {id: points, label: 좌표,   visible: true}
texts:                     # 키는 위젯이 정의한 문구 ID. 없으면 기본 문구
  panel.map.title: 지도
theme:
  light: {accent: "#1f8f66", bad: "#d33f3f"}
  dark:  {accent: "#5fd3a3", bad: "#ff6b6b"}
```

**완료 기준**
- 위젯 표와 스키마 문서가 있고, 사용자가 "편집 가능 범위"에 동의했다.
- 6절의 열린 질문이 정리됐다.

## Step 1. 관제 GUI를 명세 기반 렌더러로 전환

편집 툴이 의미 있으려면 먼저 관제 화면이 명세를 읽어 구성되어야 한다. 이 Step은 **사용자에게 보이는 변화가 없어야 한다**.

**할 일**
- `GET /api/gui_layout`: 명세를 반환한다. 파일이 없으면 코드에 내장된 기본 명세를 반환한다.
- `frontend/layout_spec.js`(새 파일)에 명세 검증, 기본값 병합, 폴백을 둔다. 이 파일은 관제 GUI와 편집 툴이 함께 쓴다.
- `app.js`의 `DEFAULT_RECTS`, `setupTabs()`, 테마 변수 적용을 명세에서 읽도록 바꾼다. 기존 "레이아웃 편집" 버튼은 이 단계에서는 그대로 두고 `localStorage` 값은 명세 위에 덮어쓰는 개인 설정으로 유지한다 (Step 3에서 정리).
- 문구는 위젯별로 `data-text-id`를 달아 덮어쓰기 가능하게 한다.

**완료 기준**
- 명세 파일이 없을 때 화면이 Step 1 이전과 픽셀 단위로 같다 (`docs/` 스크린샷과 비교).
- 명세를 손으로 고치면(패널 위치, 탭 순서, 색) 새로고침 후 반영된다.
- 깨진 명세를 넣어도 기본 화면이 뜨고 알람 바에 안내가 나온다.
- 기존 `tests/verify_step3_ui.py`, `verify_step4_ui.py`가 그대로 통과한다.

**위험**: `app.js`가 한 파일 1500줄이고 DOM ID에 직접 의존한다. 위젯을 옮겨도 ID와 이벤트 연결이 유지되도록, 위젯은 DOM을 새로 만들지 않고 **기존 요소를 재배치**하는 방식으로 시작한다.

## Step 2. 저장 API와 `/editor` 뼈대

**할 일**
- `PUT /api/gui_layout` (manager 전용): 서버 검증 → `.bak` 보관 → 파일 저장. 실패 시 이유를 항목별로 돌려준다.
- `DELETE /api/gui_layout`: 기본값으로 되돌리기 (파일 삭제 또는 기본 명세 저장).
- `GET /editor`: 편집 페이지. 로그인하지 않았거나 권한이 없으면 로그인 팝업(기존 `loginDlg` 재사용) 또는 차단 안내.
- 편집 페이지 레이아웃: 왼쪽 속성 패널 / 가운데 미리보기(`iframe`, mock) / 위쪽 도구 줄(저장, 되돌리기, 기본값, 변경 사항 보기).
- 변경 사항 보기: 저장 전 명세의 diff를 텍스트로 보여준다.

**완료 기준**
- operator 계정이나 비로그인으로 `PUT`하면 거부된다 (`tests/`에 추가).
- 비상 정지 바를 숨기거나 지우는 명세를 `PUT`하면 서버가 거부한다.
- 저장 후 다른 브라우저에서 관제 화면을 열면 같은 구성이 보인다.
- 저장 직전 파일이 `.bak`으로 남는다.

## Step 3. 패널 배치 편집

가장 체감이 큰 기능이다. 지금의 "레이아웃 편집"이 이 단계로 흡수된다.

**할 일**
- 미리보기 위에서 패널을 끌어 옮기고 가장자리를 끌어 크기를 바꾼다. 계산은 `dragRect()`를 재사용한다. 격자에 맞춰 붙고, 겹침과 범위 이탈, 최소 크기(4x3)는 막는다.
- 사이드바 탭: 목록에서 끌어 순서 변경, 눈 아이콘으로 표시/숨김, 라벨 변경. 마지막 하나는 숨길 수 없다.
- 선택한 패널의 x, y, w, h를 숫자로도 입력할 수 있다 (정밀 조정, 키보드 접근성).
- 실행 취소/다시 실행 (Ctrl+Z / Ctrl+Shift+Z), 미저장 변경 표시, 창을 닫을 때 경고.
- 해상도 미리보기: 1920x1080, 1366x768 등 프리셋과 창 크기에 따른 모양 확인.
- 관제 화면의 기존 "레이아웃 편집" 버튼 처리는 6절에서 결정한다.

**완료 기준**
- 끌기로 만든 배치를 저장하면 관제 화면에 그대로 적용된다.
- 겹치는 배치, 범위를 벗어난 배치는 저장 전에 막힌다.
- 실행 취소가 최소 20단계 동작한다.
- 비상 정지 바와 알람 바는 편집 화면에서 선택 불가로 표시된다 (잠금 아이콘).

## Step 4. 문구와 테마 편집

**할 일**
- 문구: 편집 가능한 문구 ID 목록을 위젯별로 묶어 보여주고, 입력하면 미리보기에 즉시 반영한다. "기본 문구로" 버튼. 안전 관련 문구(비상 정지, 확인 팝업 본문)는 제외한다.
- 테마: 색 토큰마다 색 선택기와 hex 입력. 라이트/다크를 각각 편집하고 미리보기에서 전환해 확인한다.
- 대비 검사: 글자색/배경색의 명암비가 4.5:1 미만이면 경고한다. 위험(`--bad`)과 경고(`--warn`), 정상(`--ok`)이 서로 구분되지 않게 바뀌면 경고한다 (상태 색은 관제 화면에서 의미가 있다).
- 글자 크기: 기본 15px 기준 12~20px 범위로 제한.

**완료 기준**
- 색과 문구를 바꿔 저장하면 라이트/다크 양쪽 관제 화면에 반영된다.
- 명암비가 낮은 조합은 경고가 뜨고, 경고를 무시하고 저장하려면 확인 단계를 거친다.

## Step 5. 위젯 추가/숨김, 프리셋, 이력 (선택)

**할 일**
- 위젯 팔레트: 코드가 제공하는 위젯 중 현재 화면에 없는 것을 탭이나 패널에 추가한다 (예: 지도 위 미니 상태 카드). 중복 배치 금지 위젯은 한 번만 허용한다.
- 프리셋: "운영용(지도 크게)", "디버그(로그, 시스템 크게)" 같은 이름 붙인 명세를 저장하고 불러온다.
- 버전 이력: 저장할 때마다 시각, 저장한 계정, 요약과 함께 보관하고 이전 버전으로 복원한다.
- 내보내기/가져오기: 명세 파일 다운로드와 업로드 (가져오기도 서버 검증을 거친다).
- 사용자(계정)별 개인 레이아웃이 필요한지는 6절 결정에 따른다.

**완료 기준**
- 프리셋 전환이 한 번의 클릭으로 되고, 이력에서 복원하면 이전 화면과 같다.
- 가져온 파일이 스키마에 어긋나면 거부되고 이유가 표시된다.

## 5. 위험과 대응

| 위험 | 대응 |
| --- | --- |
| `app.js`가 거대해서 렌더러 전환이 어렵다 | Step 1에서 겉모습 불변을 완료 기준으로 하고, DOM 재배치 방식으로 시작. 전환 중 기존 UI 테스트를 회귀 기준으로 사용 |
| 잘못된 레이아웃으로 비상 정지에 접근 못 함 | 알람 바와 비상 정지는 배치 대상이 아님 (원칙 1). 서버가 거부 |
| 저장된 명세가 깨져 관제 화면이 안 뜸 | 폴백 + `.bak` + 기본값 복원 API |
| 현장에서 누가 레이아웃을 바꿔 혼란 | manager 전용, 저장 이력(누가, 언제), 프리셋 복원 |
| 색 변경으로 경고/위험 구분 불가 | 상태 색 구분 검사 (Step 4) |

## 6. 결정이 필요한 항목

1. **저장 범위**: 서버 전체 공통 한 벌(권장, 구현 단순, 관제 PC 화면이 모두 같음) vs 계정/브라우저별 개인 레이아웃. 권장은 공통 한 벌로 시작하고 Step 5에서 개인 레이아웃을 검토하는 것이다.
2. **기존 "레이아웃 편집" 버튼**: 편집 툴로 완전히 대체(권장) vs 개인용 임시 조정으로 유지. 유지하면 `localStorage` 값이 서버 명세를 덮어써서 "저장했는데 내 화면만 다르다"는 혼란이 생길 수 있다.
3. **편집 툴의 위치**: 같은 서버의 `/editor` 페이지(권장, 인증과 API 공유) vs 별도 프로세스/포트. 별도로 두면 인증을 다시 만들어야 한다.
4. **문구 편집 범위**: 한국어 한 벌만 vs 다국어. 현재 GUI는 한국어 단일이다. 한 벌로 시작을 권장한다.
5. **위젯 추가(Step 5)를 이번 범위에 넣을지**: Step 1~4만으로도 "배치, 탭, 문구, 색 편집"이 가능하다. Step 5는 선택으로 둔다.

## 7. 권장 진행 순서

Step 0에서 6절을 정리한 뒤, **Step 1을 단독으로 끝내고 사용자가 화면이 그대로인지 확인**한다. 이 전환이 끝나기 전에는 편집 툴을 만들어도 저장할 곳이 없다. Step 1이 끝나면 Step 2~3으로 "끌어서 배치하고 저장"까지를 첫 사용 가능 시점(MVP)으로 본다.
