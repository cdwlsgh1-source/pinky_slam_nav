## 0. 공통 개요

### 0-1. 배경과 문제

관제 PC와 pinky 로봇은 Wi-Fi로 연결돼 있어서, 순찰 중 `online`이 깜빡이거나 pose가 끊기면 원인이 네트워크인지 로봇·브리지인지 화면만으로 알 수 없다. 지금은 `ros2_network_test/ros2_net_diag_v2.sh`를 **미리** 터미널에서 돌려 두고, 끊긴 뒤 로그 폴더의 파일을 시각별로 대조해야 한다 (`ros2_network_test/README.md` 6절). 끊김은 예고 없이 생기므로 스크립트를 켜 두지 않은 때의 원인은 남지 않는다.

### 0-2. 방향 결정: 외부 스크립트가 아니라 내장 수집기

| | 외부 스크립트 실행 (v1 PRD) | **내장 수집기 (이 PRD)** |
| --- | --- | --- |
| 기록 시점 | 켠 동안만 | **서버가 떠 있는 동안 항상** |
| 부하 | `/diag_test` 발행 + `ros2 topic bw` 여러 개 | 이미 받는 토픽의 바이트·도착 시각을 센다 (추가 트래픽 없음) |
| 도메인 분리(50/20/22) | `/diag_test`가 로봇 구간을 거치지 않음 | 실제 브리지된 토픽을 재므로 해당 없음 |
| 구현 | 프로세스 관리, `cwd`, 텍스트 파싱, 정지·정리 | 수집 루프 + 시계열 저장 |
| sudo | `discovery.pcap`에 필요 | 필요 없음 |
| 못 하는 것 | - | 임의 토픽 `bw`, discovery 패킷 캡처 → **스크립트는 수동 정밀 진단 도구로 남긴다** |

### 0-3. 목표와 비목표

- **목표**: (1) 로봇별 네트워크 상태를 실시간으로 보여 준다. (2) 지표를 계속 기록해서 지난 끊김을 나중에 되돌려 본다. (3) 이상이 생기면 알린다.
- **비목표**: 네트워크를 고치지 않는다(Wi-Fi, DDS 설정 변경 없음). `ros2_network_test/`는 수정하지 않는다. 패킷 분석은 하지 않는다. 로봇에 에이전트를 설치하지 않는다 (Step N4 선택 기능은 SSH 한 줄 조회만).

### 0-4. 수집 지표 (내장 수집기가 직접 구한다)

`ros2_net_diag_v2.sh`의 지표를 대응시켰다. 기준 컬럼 형식은 그 스크립트의 CSV와 맞춰 두어, 두 결과를 같은 화면 코드로 볼 수 있게 한다.

| 지표 | 대응하는 기존 파일 | 구하는 법 | 주기 |
| --- | --- | --- | --- |
| 로봇별 핑 RTT, 손실 | `ping.log` | `ping -c 1 -W 1 <IP>` 비동기 실행 | 1초 |
| 토픽별 수신 대역폭(KB/s), 수신율(Hz) | `topic_bw_*.log` | `rclpy` raw 구독으로 메시지 바이트 수와 도착 시각을 센다 (역직렬화 안 함) | 1초 집계 |
| 토픽 수신 간격 최대치(끊김 감지) | `topic_hz.log` | 같은 구독에서 마지막 수신 후 경과, 최대 간격 | 1초 집계 |
| PC 인터페이스 처리량 rx/tx KB/s | `iface_bw.csv` | `/sys/class/net/<if>/statistics/{rx,tx}_bytes` 차이 | 5초 |
| 인터페이스 에러·드랍 | `iface.log` | `/sys/class/net/<if>/statistics/*_errors,*_dropped` | 5초 |
| Wi-Fi 신호(dBm), 링크 품질 | `wifi_quality.csv` | `iw dev <if> link`, 없으면 `/proc/net/wireless`, 못 구하면 `null` | 5초 |
| PC CPU load, 메모리 % | `cpu_load.csv` | `/proc/loadavg`, `/proc/meminfo` | 5초 |
| 노드/토픽 수 | `node_count.csv` | `rclpy`의 `get_node_names()`/`get_topic_names_and_types()` (PC 도메인 기준) | 10초 |

- 측정 토픽은 **GUI가 이미 구독하는 것**: `/{id}/patrol_status`, `amcl_pose`, `battery/percent|voltage`, `odom`(현재 초당 2번만 반영, 도착은 모두 센다), 그리고 LiDAR를 켠 동안의 `scan`·`tf`. `scan`은 무겁기 때문에 항상 구독하지 않는다 (아래 결정 1).
- 참고 기준값(기존 스크립트 실측, 30분, ID20/ID22): 핑 1783건 중 `LOST` 0, 지연 약 3~7 ms, `/scan` 약 60 KB/s(메시지 5.83 KB). 정상 기준으로 쓴다 (`ros2_network_test/ros2_net_diag_20261007_*`).
- 로봇 쪽 값(CPU, 로봇 Wi-Fi 신호)은 이 방식으로는 구할 수 없다. Step N4.

### 0-5. 이 구성의 제약

- PC(도메인 50)와 로봇(20/22)은 도메인이 다르고 `domain_bridge`가 지정 토픽만 중계한다 (`CLAUDE.md` 1절). 측정은 **브리지를 거친 뒤 PC에 도착한 값**이다. 따라서 대역폭이 낮으면 Wi-Fi 문제인지 브리지 문제인지 이 값만으로는 가를 수 없고, 핑과 함께 읽어야 한다 ("핑 정상 + 토픽 부족" = 브리지/로봇 쪽 의심).
- 로봇 IP는 `config/processes.yaml`의 `ssh.host`에만 있다 (`robots.yaml`에는 없다). 결정 2.
- 상태는 서버 메모리가 기본이고 재시작하면 사라진다. 기록은 디스크에 따로 남긴다 (Step N2).

### 0-6. 아키텍처 결정

- `backend/netmon.py`(rclpy 무관 순수 로직: 집계, 등급, 파서, 저장)와 `ros_bridge.py`의 얇은 계측 훅(바이트 수·도착 시각을 넘김)으로 나눈다. 스레드 모델은 기존대로 rclpy 콜백 → `loop.call_soon_threadsafe` → 단일 태스크다 (`README.md` 구조 절).
- 핑과 시스템 지표는 `asyncio` 서브프로세스/파일 읽기로 이벤트 루프를 막지 않는다.
- 저장은 표준 라이브러리만: 메모리 링 버퍼(최근 1시간 × 1초) + 디스크 CSV 롤링 (`data/netmon/YYYYMMDD.csv`).
- 화면은 왼쪽 메뉴에 `네트워크`를 더하고 로그 화면(`logview.js`)과 같은 방식으로 전환한다. 그래프는 프레임워크 없이 Canvas, 다크/라이트 모드 색을 따른다.
- 기존 `online` 판정(5초)과 `last_seen`은 그대로 두고, 수집기는 이를 **읽기만** 한다.

### 공통 원칙

1. `ros2_network_test/`와 기존 ROS 2 코드는 수정하지 않는다. 새 코드는 `pinky_web_gui/`에만 만든다.
2. 로봇 이름과 IP는 코드에 쓰지 않고 설정에서 읽는다.
3. 수집 때문에 로봇이나 Wi-Fi에 **추가 트래픽을 만들지 않는다** (핑 1초 1패킷 외). 부하를 만드는 측정은 수동 스크립트로만 한다.
4. 각 Step은 `--mock`으로 확인할 수 있어야 한다. ROS 경로는 격리 도메인(`ROS_DOMAIN_ID=77`, `ROS_LOCALHOST_ONLY=1`)에서만 시험한다.
5. 실제 로봇 확인은 사용자가 직접 한다 (체크리스트 문서).

## Step N1. 수집기와 실시간 화면

### 범위

- **포함**: 핑·토픽 대역폭·인터페이스·Wi-Fi·CPU 수집, 등급, WebSocket 전송, 왼쪽 메뉴 `네트워크` 항목과 배지, 실시간 그래프 화면, 설정 파일, mock.

### 기능 요구사항

| ID | 요구사항 |
| --- | --- |
| FRN1-1 | `config/netdiag.yaml`에 로봇별 핑 IP(또는 `processes.yaml`의 `ssh.host` 참조), PC 무선 인터페이스(기본 자동 탐지, 못 찾으면 설정값), 수집 주기, 등급 임계값을 둔다. 코드에 로봇 이름과 IP를 쓰지 않는다. |

| FRN1-4 | 로봇별 핑을 1초마다 비동기로 실행해 RTT와 성공 여부를 기록한다. `ping`이 없으면 해당 지표만 끄고 이유를 보인다. |

| FRN1-6 | 등급 `ok`/`warn`/`bad`/`unknown`. 판정 근거를 문구로 함께 낸다: "핑 실패", "핑 정상 + 토픽 없음(브리지/로봇 의심)", "지연 증가", "손실 N%", "신호 약함". 기본 임계값은 0-4절의 실측을 근거로 설정에 두고 사용자가 고친다. |
| FRN1-7 | 왼쪽 메뉴에 `네트워크` 항목과 로봇별 등급 점. 네트워크 화면: 로봇 카드(등급, 핑, 손실, 토픽별 kbps/hz), PC 카드(처리량, Wi-Fi, CPU), 최근 5분 실시간 그래프(핑 RTT와 `LOST`, 토픽 kbps, 처리량, dBm). 그래프의 시간 범위는 5분/30분/1시간 선택. |
| FRN1-8 | WebSocket `{"type":"net", ...}`로 1초 주기 집계를 보낸다. 값이 같으면 생략하고, `snapshot`에는 최근 집계와 최근 5분 이력을 넣어 늦게 접속해도 그래프가 비지 않게 한다. |
| FRN1-9 | 읽기 전용이라 operator도 본다. 로그인이 필요하면 기존 인증을 따른다. |
| FRN1-10 | `--mock`: 가짜 값을 낸다. 시험 옵션으로 특정 로봇의 핑 실패, 지연 증가, 토픽 중단을 흉내 낸다. |

### 완료 기준

- [ ] `--mock`에서 배지와 그래프가 움직이고, 가짜 핑 실패/토픽 중단에 따라 등급과 문구가 바뀐다.
- [ ] 핑 실패와 "핑 정상 + 토픽 없음"이 서로 다른 문구로 나온다.
- [ ] 실제 연결에서 `ping` 결과, `ip -s link`의 처리량과 화면 값이 비슷하다 (사용자 확인).
- [ ] 계측 훅을 켠 상태에서 `odom`/pose 처리 지연이 늘지 않는다 (격리 도메인 부하 시험).
- [ ] 로봇 전원을 끄면 몇 초 안에 `bad`가 된다.
- [ ] 기존 소스 파일은 `ros_bridge.py` 훅 추가 외에 수정되지 않았고 `ros2_network_test/`는 수정되지 않았다.
- [ ] 단위 테스트: 핑 출력 파싱, 집계, 등급 판정, `/sys`·`/proc` 읽기 실패.

```text
5. 단위 테스트와 mock 검증. 근거는 실제 파일과 줄 번호로 제시하고 확인 못 한 것은 '확인 필요'로 표시.
```

## Step N2. 기록 보관과 지난 끊김 되돌려 보기

### 범위

- **포함**: 1초 집계를 디스크에 기록(롤링), 기간을 골라 그래프로 보기, 끊김(`LOST`/`bad`) 구간 목록과 대조, 요약, 내려받기, 보관 정리.
- **제외**: 알림 (Step N3), 로봇 쪽 지표 (Step N4).

### 기능 요구사항

| ID | 요구사항 |
| --- | --- |
| FRN2-1 | 1초 집계를 `data/netmon/YYYYMMDD.csv`에 추가한다 (`timestamp,robot,metric,value` 또는 지표별 파일; 구현 때 정하되 스프레드시트와 pandas로 바로 열 수 있어야 한다). 쓰기는 이벤트 루프를 막지 않게 버퍼링해서 한 번에 쓴다. 쓰기 실패는 경고 로그만 남기고 수집은 계속한다. |
| FRN2-2 | 보관 기간(기본 14일)과 최대 용량(기본 500 MB)을 설정으로 둔다. 서버가 시작할 때와 하루에 한 번 오래된 파일을 지운다. 지울 때 로그를 남긴다. |
| FRN2-3 | `GET /api/netmon/history?from=&to=&robot=&metrics=`: 기간의 집계를 다운샘플해서 반환한다 (30분 이상은 N초 단위로 합치고 최대값/`LOST`는 잃지 않게 min/max를 같이 낸다). 기간 상한을 둔다. |

## Step N4. 로봇 쪽 지표 (선택)

로봇의 CPU, 메모리, Wi-Fi 신호는 PC에서 알 수 없다. 끊김이 PC 쪽인지 로봇 쪽인지 가르는 데 필요하다.

### 범위

- **포함**: SSH로 로봇의 `/proc/loadavg`, `/proc/meminfo`, `/proc/net/wireless`(또는 `iw`)를 읽는 한 줄 조회, 주기 수집, 그래프에 로봇 지표 추가. **제외**: 로봇에 상주 에이전트나 스크립트 설치.

### 기능 요구사항

| ID | 요구사항 |
| --- | --- |
| FRN4-1 | 기존 SSH 실행기(`procs.py`, 키 로그인, `BatchMode`)를 재사용해 읽기 전용 고정 명령 한 줄을 10초마다 실행한다. 명령은 코드에 고정하고 브라우저 입력을 쓰지 않는다. |
| FRN4-2 | 로봇의 무선 인터페이스 이름은 로봇별 설정(`netdiag.yaml`)에 둔다 (**확인 필요**: 로봇의 Wi-Fi 인터페이스 이름). |
| FRN4-3 | SSH 접속 자체가 Wi-Fi 부하이므로 기본은 꺼 두고 화면의 토글로 켠다. 끊김 중에는 SSH가 실패하므로 마지막 성공 시각과 실패를 표시하고, 실패가 수집기를 막지 않는다 (타임아웃 3초). |
| FRN4-4 | 값은 N1 그래프의 같은 시간축에 로봇 지표로 겹쳐 그리고 N2 기록에도 남긴다. |
| FRN4-5 | `--mock`에서는 가짜 로봇 지표를 낸다. |

## Step N5. 네트워크 의심 원인 알람 (메인 화면 알람 상태바)

네트워크 연결이 의심되는 원인이 생기면 **메인 화면 위쪽의 알람 상태바**에 알람을 띄운다. 등급(양호/주의/불량)만이 아니라 "왜 의심되는지"를 문구로 알려 주는 단계다. 수집기(N1)의 지표와 등급 이벤트(N3)를 입력으로 쓴다.

> **정정 (2026-10-14, 알람바 PRD A1~A7 구현 뒤)**: 아래 "현재 알람 상태바" 설명은 N5 를 쓴 시점(알람을 브라우저 `addAlarm` 이 만들고 이력만 쌓던 때)의 것이다. 지금은 서버 `backend/alarms.py` 의 `AlarmManager` 가 알람을 만들고 활성/해소/ACK/SIL, 레벨 5단계(HH/H/L/LL/info), 소리, 이력 파일(`data/alarms/`), Alarm 화면(History·Catalog)을 이미 갖고 있다. 따라서 N5 는 **별도 `net_alarm` WS 이벤트와 `addAlarm` 확장을 새로 만들지 말고**, 규칙 평가 결과를 `AlarmManager` 알람(카탈로그 `alarms.yaml` 에 코드 추가, 같은 원인 묶기·해소는 기존 기능 사용)으로 내도록 다시 설계한다. FRN5-3(시작·해소 줄), FRN5-4(묶기), FRN5-6(`net_alarm`), FRN5-8(이력 파일), FRN5-10~11(칩·표시)이 영향을 받는다. 구현 전에 이 절을 고쳐 쓴다.

### 현재 알람 상태바 (N5 작성 시점, `frontend/index.html`, `app.js`, `style.css`)

- 구성: 칩(`connChip` 연결 상태, `zoneChip` 구역 상태) → `비상 정지` 버튼 → 알람 목록(`#alarmList`, `addAlarm(level, text)`로 `{level, text, 시각}`를 맨 앞에 추가, 최대 `MAX_ALARMS`개).
- 칩 색은 `data-level`(`ok`/`warn`/`bad`/`dim`)과 CSS 변수 `--ok`/`--warn`/`--bad`를 쓴다. 알람 목록 항목은 `.bad`/`.warn` 클래스로 색이 바뀐다.
- 현재 알람 목록은 **발생 이력을 쌓기만 하고 해소를 표시하지 않는다**. 네트워크 알람은 "지금도 진행 중인지"가 중요하므로 이 단계에서 칩 방식(진행 중 표시)을 함께 쓴다.

### 범위

- **포함**: 의심 원인 규칙, 알람 상태바 칩(진행 중)과 알람 목록(이력), 알림 상세, 해소 처리, 같은 원인 묶기, 설정, mock.
- **제외**: 소리·브라우저 알림·메일 등 외부 알림, 알람에 따른 자동 정지나 명령 변경(알람은 경고만 한다).

### 의심 원인 규칙 (초안, 임계값은 `netdiag.yaml`)

원인은 증상 조합으로 정한다. 단정하지 않고 "의심"으로 표시하며, 각 원인에 점검 안내 한 줄을 붙인다. 판정에 쓴 지표 값을 같이 보여 준다.

| 원인 코드 | 조건 (예) | 표시 문구 (예) | 레벨 |
| --- | --- | --- | --- |
| `link_down` | 핑이 연속 N회(기본 3) 실패, 토픽도 안 옴 | "pinky1: 연결 끊김 의심 (핑 3회 실패, 토픽 없음)" | bad |
| `bridge_or_robot` | 핑 정상, 토픽이 N초(기본 5) 이상 안 옴 | "pinky1: 핑은 정상인데 토픽이 안 옴 (브리지/로봇 노드 의심)" | bad |
| `latency_high` | RTT 평균이 임계값(기본 50 ms) 초과가 N초 지속 | "pinky1: 지연 증가 (평균 82 ms)" | warn |
| `packet_loss` | 창 손실률이 임계값(기본 5%) 이상 | "pinky1: 패킷 손실 12%" | warn |
| `wifi_weak` | Wi-Fi 신호가 임계값(기본 -75 dBm) 미만 (PC 쪽, N4를 켜면 로봇 쪽도) | "Wi-Fi 신호 약함 (-80 dBm)" | warn |
| `bandwidth_low` | 토픽 수신율/대역폭이 평소(최근 기준선)의 절반 미만 | "pinky1: odom 수신량 감소 (평소의 40%)" | warn |
| `iface_errors` | PC 인터페이스 에러·드랍 카운트가 증가 | "PC 네트워크 드랍 증가 (+37/5초)" | warn |
| `pc_overload` | PC CPU load가 코어 수 초과 또는 메모리 90% 이상 | "PC 부하 높음, 수신 지연 가능" | warn |
| `all_robots_down` | 모든 로봇이 동시에 `link_down` | "모든 로봇 연결 끊김 (PC 쪽 네트워크/Wi-Fi 의심)" | bad |
| `no_data` | 수집기 자체가 값을 못 구함 (핑 없음, 권한 없음 등) | "네트워크 점검 불가: 사유" | warn |

- 한 로봇에 여러 원인이 겹치면 가장 심한 것을 대표로 보이고 나머지는 상세에 둔다. `all_robots_down`이면 로봇별 `link_down` 알람은 묶어서 하나로 보인다 (원인이 PC 쪽일 가능성이 높기 때문).
- 로봇이 `offline`이고 사용자가 정지시킨 것이면(`processes.yaml`로 bringup을 끈 경우) 알람을 내지 않는다 (**확인 필요**: 정지 의도를 수집기가 알 수 있는지).

### 기능 요구사항

| ID | 요구사항 |
| --- | --- |
| FRN5-1 | 알람 상태바에 `네트워크` 칩을 더한다 (`connChip`, `zoneChip` 옆). 정상이면 "네트워크: 양호"(`ok`), 의심 원인이 있으면 가장 높은 레벨과 개수("네트워크: 의심 2건")를 `warn`/`bad`로 표시한다. 수집 전이면 `dim`. 기존 칩과 같은 `setChip(id, level, text)` 방식을 쓴다. |
| FRN5-2 | 칩을 누르면 진행 중인 의심 원인 목록(로봇, 원인 문구, 시작 시각, 경과 시간, 판정에 쓴 값, 점검 안내)을 펼친다. 거기에서 `네트워크` 화면으로 가는 링크를 둔다. |
| FRN5-3 | 새 의심 원인이 **시작될 때** 알람 목록(`addAlarm`)에 `bad`/`warn` 한 줄을 추가하고, **해소될 때** `ok`성 한 줄("pinky1: 연결 복구, 42초간")을 추가한다. 이력은 기존 `MAX_ALARMS` 한도를 따른다. |
| FRN5-4 | 깜빡임 방지: 원인은 조건이 N초(기본 3) 이어져야 시작하고, 조건이 N초(기본 5) 풀려 있어야 해소한다. 같은 원인의 재알람은 쿨다운(기본 60초) 안에서 한 건으로 묶고 반복 횟수를 표시한다. |
| FRN5-5 | 같은 증상은 한 건으로 묶는다: 로봇 둘이 동시에 `link_down`이면 `all_robots_down` 하나로, PC 쪽 원인(`wifi_weak`, `iface_errors`, `pc_overload`)은 로봇별로 반복하지 않는다. |
| FRN5-6 | 백엔드가 규칙 평가와 알람 상태(진행 중 목록, 이력)를 가진다. 브라우저는 표시만 한다. 새로 접속한 화면도 `snapshot`으로 진행 중 알람을 바로 받는다 (WebSocket `{"type":"net_alarm", ...}`, 변경 시에만). |
| FRN5-7 | 규칙마다 켜고 끄기, 임계값, 지속 시간을 `config/netdiag.yaml`에서 바꾼다. 잘못된 값이면 서버가 시작할 때 오류를 낸다 (N3와 같은 방식). |
| FRN5-8 | 알람 이력은 N2 기록과 같은 시간축에서 볼 수 있게 `data/netmon/`에 이벤트(시작, 해소, 원인, 값)로 남긴다. 네트워크 화면의 "끊김 목록"(FRN2-4)과 같은 항목으로 연결한다. |
| FRN5-9 | 서버를 켠 직후 N초(기본 10초)는 기준선과 연결 상태가 정해지지 않았으므로 알람을 내지 않는다 ("시작 중"). 로봇이 아직 한 번도 안 온 상태(`online: null`)를 끊김으로 취급하지 않는다. |
| FRN5-10 | 읽기 전용 알람이라 operator에게도 보인다. 비상 정지 버튼 배치와 알람 목록 줄바꿈이 깨지지 않게, 좁은 화면(860px 이하)에서는 칩이 알람 목록 위 줄로 내려간다. |
| FRN5-11 | 색만으로 구분하지 않는다: 레벨 아이콘/문구(주의, 불량)를 함께 쓴다. 라이트/다크 모드 색을 따른다 (`--ok`/`--warn`/`--bad`). |
| FRN5-12 | `--mock`에서 원인별 장애를 흉내 낼 수 있다 (핑 실패, 토픽 중단만, 지연 증가, 손실, 신호 약함, 두 로봇 동시 끊김). 예: `--mock-net-fault pinky1:link_down,all:wifi_weak` (이름은 구현 때 정한다). |

### 완료 기준

- [ ] mock의 핑 실패에서 알람 상태바에 `네트워크: 의심 1건`(bad) 칩과 알람 목록 한 줄이 뜨고, 복구하면 칩이 `양호`로 돌아오고 복구 줄이 남는다.
- [ ] "핑 정상 + 토픽 없음"과 "핑 실패"가 서로 다른 원인 문구로 나온다.
- [ ] 두 로봇이 동시에 끊기면 `all_robots_down` 한 건으로 묶인다.
- [ ] 1~2초의 짧은 지연으로는 알람이 뜨지 않고, 같은 원인이 반복돼도 쿨다운 안에서는 한 건으로 묶인다 (단위 테스트).
- [ ] 서버 시작 직후와 로봇이 아직 안 온 상태에서는 알람이 나지 않는다 (단위 테스트).
- [ ] 새로 접속한 브라우저가 진행 중인 알람을 바로 본다.
- [ ] 860px 이하 화면과 다크 모드에서 알람 상태바가 깨지지 않는다 (headless Chrome 화면 검증과 스크린샷).
- [ ] 임계값을 `netdiag.yaml`에서 바꾸면 반영되고, 잘못된 값은 시작 오류가 난다.
- [ ] 기존 알람(연결, 구역)과 비상 정지 동작은 그대로다 (기존 UI 테스트 통과).
- [ ] 실제 로봇에서 와이파이를 끊었을 때 알람이 뜨는지는 사용자가 확인한다 (체크리스트 문서).

### Claude Code 프롬프트

```text
pinky_web_gui 의 메인 화면 알람 상태바에 네트워크 의심 원인 알람을 추가해줘. ros2_network_test 와 기존 파일은 수정하지 마(알람바 칩과 net_alarm 처리 추가 제외).
1. backend/netalarm.py(rclpy 무관, 시계 주입): netmon 의 지표와 등급 이벤트를 입력으로 의심 원인 규칙(link_down, bridge_or_robot, latency_high, packet_loss, wifi_weak, bandwidth_low, iface_errors, pc_overload, all_robots_down, no_data)을 평가. 지속 시간 필터, 해소 지연, 쿨다운, 같은 증상 묶기, 서버 시작 직후 유예. 규칙 설정은 config/netdiag.yaml 이고 잘못되면 시작 오류.
2. WebSocket net_alarm 메시지와 snapshot(진행 중 목록). 이력은 data/netmon 에 이벤트로 기록.
3. 프론트엔드: 알람 상태바(frontend/index.html 의 alarmbar)에 '네트워크' 칩을 setChip 방식으로 추가, 클릭 시 진행 중 원인 목록(문구, 경과, 판정 값, 점검 안내), 시작/해소 때 addAlarm 한 줄 추가. 좁은 화면과 다크 모드 확인.
4. --mock 에서 원인별 장애 흉내 옵션. 단위 테스트(지속, 쿨다운, 묶기, 유예)와 mock 검증, headless Chrome 화면 검증.
근거는 실제 파일과 줄 번호로 제시하고 확인 못 한 것은 '확인 필요'로 표시해줘.
```

## 5. 결정이 필요한 항목

1. **측정할 토픽 범위**: 기본은 이미 받는 토픽(`patrol_status`, `amcl_pose`, `battery`, `odom`)만이다. 가장 큰 트래픽인 `scan`(약 60 KB/s)과 `tf`는 LiDAR를 켠 동안만 측정되고, 항상 재려면 상시 구독이 필요해 Wi-Fi 부하가 늘어난다. 상시 측정 토글을 둘지, 기본은 어느 쪽일지.
2. **로봇 IP 기준 위치**: `processes.yaml`의 `ssh.host` 재사용(두 곳이 어긋나지 않음) vs `netdiag.yaml`에 따로.
3. **Step N4(로봇 쪽 지표)를 이번 범위에 넣을지.** SSH 조회도 Wi-Fi 부하이고 로봇 인터페이스 이름 확인이 필요하다.
4. **기록 보관**: 위치(`data/netmon/`), 기간(기본 14일), 용량(기본 500 MB), `.gitignore` 포함 여부. 24시간 기록의 예상 크기는 구현 중 측정해서 정한다.
5. **등급 임계값**: 0-4절의 정상 실측만 있다. 끊김이 있던 날의 로그나 경험치가 있으면 기준으로 삼는다.
6. **기존 스크립트의 위치**: 수동 정밀 진단(`/diag_test` 부하, `discovery.pcap`, `ros2 topic bw`)으로 그대로 두고 GUI에는 "스크립트 사용법" 안내만 둘지, 후속으로 결과 폴더를 GUI에 가져와 같은 그래프로 볼 수 있게 할지.
7. **핑 주기**(기본 1초)와 서버가 직접 핑을 보내도 되는지. Wi-Fi 부하가 걱정되면 2~5초로 늘린다.
8. **의심 원인 규칙의 기본 임계값**(Step N5): RTT 50 ms, 손실 5%, 신호 -75 dBm, 끊김 판정 3회/5초 등은 초안이다. 정상 실측(핑 3~7 ms, 손실 0)만 근거라서, 실제 끊김을 겪은 로그가 있으면 맞춘다.
9. **알람 표시 방식**(Step N5): 진행 중 알람은 칩, 발생·해소 이력은 알람 목록으로 나눈 안이 기본이다. 칩 없이 알람 목록만 쓸지(기존 방식 유지, 해소 표시 없음) 결정이 필요하다.
10. **정지시킨 로봇의 알람**(Step N5): GUI로 bringup을 끈 로봇은 의도된 정지이므로 알람을 내지 않는 안이 기본이다. 수집기가 정지 의도를 알 수 있는지 확인이 필요하다.
